# Milestone 12 operations and measurement guide

## Architecture and prerequisites

- Production origin: `https://scouty.ca` (HTTPS apex is canonical).
- Client: Expo SDK 57, React Native Web, and Expo Router static output. Client-side navigation is SPA navigation after the initial static document.
- Server: Express and TypeScript on Render.
- Database: MySQL 5.7 with numbered SQL migrations run by `npm run db:migrate --prefix server`.
- Frontend: static `dist/` uploaded to HostGator. Build with `npm run export:web` so search assets and `.htaccess` are included.
- Privacy page and persistent Analytics preferences footer control: implemented.
- Administrator role and analytics HTTP API: not present. Milestone 13 must add server-side authorization before exposing reports.
- Authoritative DNS provider: not documented in this repository. The owner must inspect the domain's authoritative nameservers or registrar before adding Search Console's TXT value.

## Environment configuration

Local, test, preview, and staging defaults:

```text
EXPO_PUBLIC_ANALYTICS_ENABLED=false
EXPO_PUBLIC_GOOGLE_ANALYTICS_ID=G-XXXXXXXXXX
EXPO_PUBLIC_SITE_INDEXING_ENABLED=false
```

Production only:

```text
EXPO_PUBLIC_ANALYTICS_ENABLED=true
EXPO_PUBLIC_GOOGLE_ANALYTICS_ID=<the production GA4 web-stream measurement ID>
EXPO_PUBLIC_SITE_INDEXING_ENABLED=true
```

`JAMES_CONFIGURATION_VERSION_ID` is an optional server value using letters, numbers, `.`, `_`, or `-` (maximum 64 characters). It is copied into new operational events and is nullable until Milestone 13 manages James configuration versions. The client cannot set it.

## Consent design

Consent begins as unset and GA is not present in static HTML. The first-party local-storage key `scouty.analytics-consent.v1` stores only `accepted` or `declined`; it is separate from authentication cookies. The banner gives equal Accept analytics and Decline analytics controls. The footer opens the same preferences later. Withdrawal sends denied consent, activates GA's disable flag, stops future events, and attempts to delete `_ga` and `_ga_*` first-party cookies. Browser/domain rules may prevent deleting every previously created cookie.

GA loads only in a browser after acceptance, when `NODE_ENV=production`, the enabled flag is exactly `true`, and the ID matches `G-...`. Initialization is single-flight, page paths are allowlisted, query strings/fragments are discarded, and duplicate route views are suppressed.

## External GA4 allowlist

| Event | Parameters |
| --- | --- |
| `page_view` | allowlisted route, safe page title |
| `search` | media type, genre/provider/language count buckets, authenticated boolean |
| `recommendations_viewed` | result-count bucket, response-time bucket |
| `recommendation_opened` | position bucket, media type (contract reserved; no current product open action) |
| `filter_applied` | filter category, selected-count bucket |
| `watchlist_added` | media type, source surface |
| `feedback_submitted` | positive or negative only |
| `sign_up` | email method category |
| `login` | email method category |
| `contact_submitted` | success only |

The analytics service rejects unknown events, unknown/missing parameters, nested values, arrays, free text, full URLs, and values outside its enums. No prompt, title, email, username, account ID, token, message, error, or Letterboxd detail is accepted.

## Internal operational events

The server supports: `recommendation_requested`, `recommendation_completed`, `recommendation_failed`, `recommendation_opened`, `recommendation_saved`, `recommendation_feedback`, `letterboxd_sync_completed`, `letterboxd_sync_failed`, `registration_completed`, `verification_email_succeeded`, `verification_email_failed`, `contact_submission_succeeded`, and `contact_submission_failed`.

Only strict columns are stored: event ID, minute-coarse UTC timestamp, request-scoped recommendation correlation UUID, nullable configuration version, approved buckets/enums, bounded filter counts, and authenticated boolean. There is deliberately no arbitrary JSON/free-text column and no user ID, session ID, IP, user agent, referrer, URL, prompt, title, email, username, token, request body, stack trace, or provider payload.

The recommendation correlation UUID is generated by the server for one recommendation request. It is not a user/session/device identifier and is used only to connect completion, save, and feedback outcomes. Metrics start after migration `0009`; no personal history is reconstructed.

## Aggregates and rates

All boundaries are UTC `[00:00:00, next 00:00:00)`. A retry deletes and transactionally rebuilds that UTC day. A compact SHA-256 dimension key enforces one aggregate row per dimension set without a wide MySQL 5.7 index, making retries idempotent and concurrent duplicates rejectable. Zero denominators return a rate of `0`.

- Successful recommendation rate: completed searches with `success` / all completed searches.
- Empty-result rate: completed searches with `empty` / all completed searches.
- Failure rate: failed requests / requested recommendations; grouped by safe failure category.
- Open rate: distinct correlated open requests / completed searches. It remains zero until Scouty has a real recommendation-open action.
- Save rate: distinct correlated saves / completed searches.
- Positive/negative feedback rates: category count / all feedback category events.
- Helpful recommendation rate: distinct same-UTC-day request correlations with at least one save or positive feedback / completed searches.
- Already-watched reports: `already_watched` feedback category count only.
- Response performance: completed-event histogram plus median and p95 bucket. Exact averages are intentionally unavailable because exact latency is not retained.
- Letterboxd, registration, verification-email, and contact metrics are success/failure counts.
- Repeat-title rate is intentionally unavailable because calculating it would require retaining title-level history.

Raw events are retained for 90 days. Daily non-identifying aggregates may be retained longer. Run after midnight UTC with the production scheduler:

```bash
npm run analytics:maintain --prefix server
```

The command aggregates the previous UTC day and deletes at most 5,000 expired raw rows per run. To retry a day safely, set `ANALYTICS_AGGREGATE_DATE=YYYY-MM-DD` for that invocation. Schedule repeated bounded runs if a backlog exceeds 5,000 rows. The JSON result reports the day and deleted-row count.

## Route indexing matrix

- Public/indexable/sitemap: `/`, `/about`, `/contact`, `/privacy`, `/terms`.
- Public/noindex: `/explore`, `/login`, `/signup`, `/forgot-password`.
- Token/action/noindex: `/verify-email`, `/reset-password`.
- Authenticated/noindex: `/profile`, `/profile/edit`, `/profile/library`, `/profile/preferences`, `/profile/streaming-services`.
- Unknown, callback, and future admin paths: fallback `noindex`; never added to the sitemap.

Public pages receive unique titles, descriptions, Open Graph basics, and absolute canonicals. Private routes receive `noindex,nofollow,noarchive`. The generated sitemap includes only the five public canonical URLs and no fabricated `lastmod`. Production `robots.txt` allows crawling and references `https://scouty.ca/sitemap.xml`; preview/staging generation blocks all crawling. Robots rules are not access control. `.htaccess` redirects HTTP and non-apex hosts to the HTTPS apex.

## Owner setup and verification

1. Add the production `G-...` measurement ID and `EXPO_PUBLIC_ANALYTICS_ENABLED=true` to the frontend production build environment. Do not add the ID to DNS.
2. Set `EXPO_PUBLIC_SITE_INDEXING_ENABLED=true` only for the production build. Keep analytics and indexing disabled in preview/staging unless using a separate test property intentionally.
3. In GA4 enhanced measurement, disable site search, form interactions, outbound-click collection, and any feature that could collect user-controlled URLs or form/search content. Keep Google Signals, advertising personalization, remarketing, and ad features disabled.
4. Review the production Privacy page and consent UI with the owner/legal reviewer before enabling analytics.
5. Build with `npm run export:web`, then deploy through the normal HostGator process. Run migration `0009` through the normal migration command before server instrumentation is enabled.
6. In a clean browser, verify before consent that there is no `googletagmanager.com` request, `_ga` cookie, `dataLayer`, or GA event.
7. Accept analytics and verify one loader/configuration plus one initial page view and one sanitized page view per SPA navigation in GA4 DebugView or Realtime.
8. Decline or withdraw and verify that future GA requests stop. Confirm first-party `_ga` cookies are removed where browser rules permit.
9. Inspect requests and confirm no payload contains PII, raw prompts, tokens, full URLs, titles, private identifiers, messages, or error text.
10. Create or open the Google Search Console domain property for `scouty.ca`.
11. Obtain Google's Search Console TXT verification value and add that exact TXT record at the authoritative DNS provider identified from the domain's nameservers.
12. Verify ownership after DNS propagation. The Search Console TXT value is separate from the GA measurement ID.
13. Submit `https://scouty.ca/sitemap.xml`.
14. Inspect `/`, `/about`, `/privacy`, `/login`, `/reset-password`, and `/profile` in Search Console to confirm public indexing and private `noindex` behavior.
15. Link Search Console and GA4 only if desired and only with the appropriate Google account permissions.
